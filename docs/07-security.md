# 07 — 安全

Cloud Core 把界面权威移到服务端。服务端必须把每个入站字节都当作敌意输入，客户端必须把每个入站文档
当作"来自可信权威、但仍需限制"的数据。

## 0. 事件限流（已实现）

- 每个玩家一个令牌桶：20 次/秒、突发 40（`EventRateLimiter`）。这两个值是硬编码的，
  `config.yml` 里没有对应键。
- 超限不执行动作，回 `EVENT_RESULT(RATE_LIMITED)` 并写 `Rate limited EVENT` 日志。
- 玩家退出时丢弃该玩家的桶；时钟可注入，规则有单元测试。
- 真机验证：对“+1”按钮连发 120 次点击，服务端记录 14 条 `Rate limited EVENT`。
- 动作冷却（`cooldown` 动作、`per-element-cooldown-ms`）**尚未实现**。

## 0.1 command 动作的闸门（已实现）

- 默认 `actions.commands.enabled: false`，页面里的 `command` 一律拒绝。
- 开启后按**第一个词**精确匹配 `actions.commands.allowlist`（忽略大小写、允许前导斜杠）。
- 拒绝时回 `EVENT_RESULT(REJECTED)` 并记录 `Blocked command action ...` 日志。
- 执行走 `Bukkit#dispatchCommand`，`as: console` 需要显式声明。

## 1. 资产与信任边界

| 资产 | 威胁 | 边界 |
| --- | --- | --- |
| 服务端状态（物品栏、经济） | 伪造点击、重放、竞态 | 主线程 `EVENT` 校验 |
| 玩家客户端稳定性 | 崩溃循环、内存耗尽、渲染损坏 | 有界解码、故障隔离 |
| 服务端内存 | 超大文档、分片洪泛、贴图刷屏、遍历爆炸 | 按玩家/会话/文档的上限 |
| 玩家数据 | 输入文本泄漏进日志 | 日志脱敏 |
| 服务端文件系统 | 通过贴图键/页面 id 做路径穿越 | 严格校验 id |
| 其他插件 | 物品栏点击被劫持 | `passthrough`，旧界面路径不取消事件 |
| 其他模组 | Tooltip/Boss/HUD 钩子冲突 | 窄钩子、可回退、优先级评审 |

信任假设：

- 服务端插件是可信代码。
- 客户端模组只对**它自己的用户**负责正确渲染；它可以对一切撒谎。
- 第三方插件的物品栏对其自身点击是权威的。`passthrough` 模式下绝不拦截。
- 原版 `BossEvent`、物品提示内容不是攻击面，但它们的标题/文本会进入我们的渲染器，必须按不可信文本
  处理长度和字符。

## 2. 校验矩阵

每个入站报文经过同一道门（标注为"未实现"的步骤目前不存在）：

1. **通道**精确匹配 `cloudcore:main`。
2. **帧**魔数、版本、标志位、长度、varint 边界。
3. **限流**玩家级令牌桶。
4. **握手**完成且主版本匹配。
5. **操作码**已知且允许在当前会话状态使用。
6. **会话**存在、属于该玩家、面板类型与当前绑定一致。
7. **修订号**不早于会话当前修订号。
8. **元素/动作**存在于编译后的文档，且动作绑定到该元素和事件。
9. **载荷**类型匹配动作 schema；大小在限额内。
10. **权限**（动作声明；页面 `permission:` 在 `sendPage`/API `open`/`open_page`/刷新处强制）。
11. **冷却**（未实现）。
12. 执行。

失败返回 `EVENT_RESULT(REJECTED, 原因枚举)` 并计数；消息是固定枚举名，不含内部细节。

### 2.2 逐报文规则

**当前实现**只做了帧解码、限额、握手状态、会话/令牌匹配、事件限流与动作权限；
下表的"每 5 秒一次""每键 30 秒"等频率限制属于设计目标。

| 报文 | 检查 |
| --- | --- |
| `HELLO` | 版本格式；语言 ≤ 16 字节；guiScale 1..16；尺寸 ≤ 16384（每 5 秒一次尚未实现） |
| `UI_READY` | 会话存在；令牌匹配；surface 匹配；修订号 ≤ 会话修订号 |
| `EVENT` | 第 6–11 步；载荷深度 ≤ 16；map ≤ 64；字符串 ≤ 512 |
| `UI_CLOSED` | 会话存在；原因在枚举内 |
| `TEXTURE_REQUEST` | 键语法；只代理当前玩家页面里出现过的键（每键 30 秒一次尚未实现） |
| `PONG` | nonce 匹配 |
| `CLIENT_ERROR` | 已定义，两端未接线 |
| `METRICS` | 已定义，两端未接线 |
| `SCREEN_PROBE` | 已定义，两端未接线 |

## 4. 文本清洗

服务端发送前：

- 单字段最多 512 字符，单文档最多 32,768 字节。
- 去除 C0/C1 控制字符（多行字段允许 `\n`）。
- 去除双向覆盖/隔离字符（`U+202A..U+202E`、`U+2066..U+2069`）和零宽字符
  （`U+200B..U+200D`、`U+FEFF`）。
- `§` 格式码解析成文本段；无法解析的按字面量。
- 绝不把客户端输入拼进命令字符串。

客户端渲染前：

- 重新应用长度上限。
- 单个标签最多 64 个文本段。
- 不解析 `${...}`。
- Tooltip 内容来自原版/其他模组时同样做长度和字符清洗，避免超长行撑爆布局。

### 4.1 敏感输入框

- 文档 `sensitive: true` 的输入框：客户端掩码显示，服务端仍收到原文用于校验。
- 原文绝不写日志、绝不进调试输出、绝不作为 `message` / `title` 回显。
- 服务端重新校验长度、字符集和过滤器；不依赖客户端掩码或客户端过滤。
- 不要把敏感值拼进 `command` 动作；用专用 `ActionHandler` 处理。
- `change` 事件同样受 250 ms 防抖和服务端限流。
- 连接本身由 Minecraft 登录后的加密层保护；Cloud Core 不额外加密，因为不掌握会话密钥。

## 6. 贴图、URL 与字体

- `TEXTURE_PUT` 只接受 PNG，客户端先校验 8 字节签名。
- 上传前检查尺寸与解码后内存；超出会话预算拒绝。
- 键清洗，不从键派生文件系统访问；动态贴图注册在 `cloudcore:dynamic/<key>`。
- `local:` 路径必须规范化后仍位于 `.minecraft/resourcepacks/CloudCore/` 下；允许中文业务目录，
  拒绝 `..`、绝对路径、符号链接、控制字符、双向控制符、Windows 保留名、尾随点/空格和大小写冲突。
- 路径总长 ≤ 256 字符；UTF-8 + NFC 归一化；允许 Unicode 字母/数字/空格/`_ - . /`，但首尾不能是
  空格或点；扩展名白名单 png/gif/ttf/otf。
- 字体只能来自客户端本地 CloudCore 目录、资源包或模组最小回退；服务端不能推送字体文件。
- 页面 id、片段路径、字体标识符都做字符集和长度校验，禁止 `..` 和绝对路径。

### 6.1 URL 贴图

默认是**客户端直连**：服务端只发 `TEXTURE_REF`，图片字节不占游戏连接。服务端代理是可选模式。

客户端直连（`RemoteTextureCache.isSafeRemoteUrl`，已实现）：

- 只允许 `https://`；拒绝 `file:`、`jar:`、`http:`、带用户信息的 URL 和非 443 端口。
- 解析 DNS 后拒绝私有、回环、链路本地、组播、保留地址与 IPv6 `fc00::/7`。
- 不跟随重定向（`HttpClient.Redirect.NEVER`）；3xx 直接失败，避免跳转绕过主机/IP 检查。
- 超时 10 秒，最大 8 MiB；流式读取，超限立即中止。
- 按扩展名/魔数识别 PNG 与 GIF（当前不支持 JPEG），不信任 `Content-Type`。
- 不发送 cookie、认证头或自定义敏感头；User-Agent 明确标识 Cloud Core。
- 服务端提供的 SHA-256 非空时必须校验；缓存按内容哈希命名，加载时再次校验。
- 缓存目录不允许符号链接逃逸；损坏文件直接丢弃。
- 隐私：图片主机能看到玩家 IP。客户端 `remoteImages=false` 时禁止直连，改为请求服务端代理或显示占位。
- DNS 重绑定仍有残余风险；高安全场景使用 `proxy` 模式。

服务端代理：

- 主机必须在显式允许列表内；每一跳都做 DNS/IP 检查。
- 禁止 `file:`、`jar:`、`http:` 和非标准端口。
- 超时、大小、重定向、魔数识别同上。
- 按 URL + 内容 SHA-256 缓存；失败不缓存。
- 管理员可以完全关闭 URL 贴图。

带宽取舍：`client` 模式下服务端只发引用，玩家多时不会产生 N 倍图片上行；`proxy` 模式下服务端
上行 = 玩家数 × 图片字节，只适合小规模、隐私要求高或客户端出网受限的场景。

### 6.2 GIF

- `client` 模式由客户端解码；`proxy` 模式由服务端解码，客户端只接收精灵表 PNG。
- 帧数 ≤ 64；单帧 ≤ 512×512；解码后总大小 ≤ 16 MiB；最小帧延迟 50 ms；编码后精灵表 ≤ 1 MiB。
- 解码器按帧读取并累计像素，超限立即中止，不先分配全部帧。
- 合成到统一画布后再编码为 PNG；直连模式原始 GIF 只存在于客户端缓存，代理模式不发给客户端。
- 失败回退第一帧或缺失贴图。

### 6.3 NanoVG、原生库与字体

- 只加载随模组打包的 NanoVG 原生库；不从服务端或网络下载 `.dll` / `.so` / `.dylib`。
- 解压目录最小权限；加载前校验文件哈希/大小；加载失败回退 `NativeBackend`。
- TTF/OTF 来自本地 CloudCore 目录、资源包或模组回退；单文件 ≤ 8 MiB，解析失败回退内置字体，
  不执行任何嵌入代码。
- 字体来自客户端本地 CloudCore 目录或资源包；不接受服务端通过插件消息直接推送字体文件。
- FBO 尺寸由屏幕和 GUI 缩放限制；单层显存上限 8 MiB，超过时降 `fboScale` 或回退原生。
- NanoVG image/font handle 有数量与内存上限，`F9` 或资源包重载时释放。
- 文档不能指定自定义 shader/GLSL；渲染后端只使用内置管线。

## 7. 动作安全

- 客户端只能命名文档中存在的 `(elementId, actionId)` 对。
- 动作体、命令、权限和 `state` 不下发客户端；客户端只拿到 actionId 映射，无法读取命令内容。
- `command` 默认关闭；开启后只有 allowlist 里的首个词能执行，`as: player` 走玩家权限，`as: console`
  需要管理员显式声明。
- 自定义 `ActionHandler` 是编译代码，且可声明 `permission()`；未注册的动作名在运行期被拒绝。
- 动作参数来自会话状态和模板，不来自原始载荷，除非文档显式绑定。
- 模板在命令动作中引用事件载荷时，校验器警告。
- 冷却在执行前检查。
- 遍历展开在服务端进行，客户端不能提交实例列表或实例数量。

### 7.1 占位符解析

- 默认在主线程同步解析；PlaceholderAPI 扩展不保证线程安全。
- 每玩家 2 ms/tick、全局 10 ms/tick 预算；超出推迟到下一 tick。
- 解析结果按不可信文本处理：长度上限、控制字符清洗，不参与命令拼接。
- 异步只允许配置中显式列出的命名空间；结果下一 tick 应用到主线程。
- 客户端不解析占位符。

## 8. 物品栏完整性

- 后备 `Inventory` 是槽位内容的唯一事实来源。
- `managed` 取消已声明网格之外的点击；`readonly` 取消全部；`passthrough` 不干预。
- 客户端绝不会被告知槽位里有容器未同步的物品。
- 装饰物品是数据副本，不是槽位内容。
- 玩家背包面板不改变 `InventoryMenu` 逻辑；服务端只推皮肤。
- 创造模式物品栏不在 v1 范围，避免误伤创造模式状态。

## 9. 客户端隔离

- 不根据文档内容做反射、类加载、脚本执行或表达式求值。
- 文档使用严格 Gson 配置：限制嵌套深度、不使用多态适配器；同主版本忽略未知字段以支持次版本追加，
  未知元素类型/枚举值拒绝。
- 每个面板钩子独立捕获异常；一个面板失效不影响其他面板。
- 任何解析或渲染失败都降级到原版。
- 会话在 3 次客户端错误后禁用；服务端收到 3 次 `CLIENT_ERROR` 后停止发送。
- 混入只改写匹配待绑定的 `Screen` 参数、物品提示、滚轮和 Boss 血条绘制；不影响其他逻辑。

## 10. 日志与隐私

- 不记录报文 body。
- 不记录输入框内容、令牌、密码或会话密钥。
- `SCREEN_PROBE` 只在有待绑定项时发送，标题截断并去格式码。
- 日志中的玩家标识是 UUID 加名字，不含 IP。
- 异常堆栈记录文档 id 和元素 id，不记录载荷内容。
- Tooltip 内容可能包含其他模组注入的文本，不写入日志。
- URL 只记录 `scheme://host/path`，去掉 query/fragment；服务端路径只用相对路径。
- 日志写入前清洗 `\n`、`\r`、`\t` 和 Unicode 方向控制符，防止日志注入。
- `DIAGNOSTIC.detail` 截断到 4 KiB，同一错误 10 秒去重，避免刷屏/放大。
- 客户端日志和诊断包默认脱敏；`logRedaction=false` 只允许在本地开发使用。

## 11. 滥用场景与响应

| 场景 | 响应 | 现状 |
